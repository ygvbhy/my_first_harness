# 에이전트 정의

## 에이전트 정의 파일 = 역할 계약서

- 담당, 판단 기준, 소통 방식을 명시한 문서

### 프론트매터

- 이름, 설명, 모델, 도구처럼 외부에서 이 에이전트를 식별하고 호출하는 데 필요한 정보가 담긴다.
- "프론트매터는 서브에이전트의 메타데이터와 설정을 정의하고, 본문은 서브에이전트의 행동을 이끄는 시스템 프롬프트가 된다."
- ex) 프론트매터가 명함이라면 본문은 그 에이전트가 일하는 방식을 담은 내부 지침서

### 본문 7개 섹션 - 왜 필요하고 어떻게 쓰는가

1. 핵심 역할 - 범위 결정
   하는 일을 1~3개로 명시한다는 것은, **하지 않는 일도 함께 경계 짓는다**는 뜻.

나쁜 예

```text
## 핵심 역할
- 세계관을 만든다.
```

좋은 예

```text
## 핵심 역할
1. 세계의 물리 법칙과 기술 수준 정의
2. 사회 구조, 젗이 체계, 경제 시스템 설계
3. 역사적 맥락과 현재 갈등 구조 수립
4. 장소별 환경과 분위기 묘사
```

좋은 예는 '무엇을 하는가'와 함께 '무엇을 다루는가'를 명확히 밝힌다.

2. 작업 원칙 - 판단 기준 결정
   **두 선택지가 충돌할 때 어느 쪽을 택할지** 알 수 있어야 한다.

나쁜 예

```text
## 작업 원칙
- 최선을 다한다.
- 품질을 높인다.
- 빠르게 작업한다.
```

좋은 예

```text
## 작업 원칙
- PASS/FIX/REDO 3단계로 명확히 판정
- FIX는 부분 수정으로 해결 가능한 경우, REDO는 전면 재생성 필요
- 주관적 취향이 아닌 객관적 기준(일관성, 가독성, 구도)으로 판단
```

- 두 선택지 앞에서 어느 쪽을 택할지 알 수 있어야 한다.
- 규칙의 이유가 담겨야 한다.
- 이 에이전트만의 특성을 드러내야 한다. 일반론으로 채우면 다른 파일과 복사 - 붙여넣기가 된다.

3. 입출력 프로토콜 - 에이전트 간 API 계약
   다른 에이전트가 이 에이전트의 산출물을 읽을 경로와 형식을 정한다. 프론트엔드가 백엔드 API의 응답 형식을 알아야 하듯, 다음 에이전트는 이전 에이전트의 출력 위치와 형식을 알아야 한다.

나쁜 예

```text
## 핵심 역할
1. 세계관 설계
2. ...
```

입출력이 빠지면 에이전트는 결과를 어디에 둘지 매번 즉흥으로 결정한다.

좋은 예

```text
## 입력/출력 프로토콜
- 입력: 사용자의 세계관 컨셉, 장르 요구사항
- 출력: `_workspace/01_worldbuilder_setting.md`
- 형식: 마크다운. 섹션별 (물리/사회/기술/역사/장소)
```

4. 팀 통신 프로토콜 - 누구에게, 무엇을, 언제
   SendMessage 도구로 주고받을 정보의 세 요소, 즉 누구에게 / 무엇을 / 연제를 명시한다.

나쁜 예

```text
## 팀 통신 프로토콜
- 필요하면 다른 에이전트에게 메시지를 보낸다.
```

좋은 예

```text
- character-designer에게: 사회 구조, 계급 시스템, 직업 군 정보 SendMessage
- plot-architect에게: 세계의 주요 갈등 구조, 위기 요소 SendMessage
- science-consultant로부터: 과학적 오류 피드백 수신 -> 설정 수정
- 세계관 변경 시 관련 팀원 전체에 브로드캐스트
```

꼭 기억할 원칙 **좋은 메시지 = 발견 사실 + 수신자가 취해야할 행동**

5. 에러 핸들링 - 종료 조건 명시
   구체적인 실패 시나리오, 각 시나리오에서의 행동, 최대 재시도 횟수를 정해 둔다. 이것이 빠지면 에이전트는 예상치 못한 상황에서 무한 대기하거나, 잘못된 결과를 조용히 넘기거나, 팀 전체를 멈춰 버린다.

나쁜 예

```text
## 에러 핸들링
- 실패 시 재시도한다.
```

좋은 예

```text
## 에러 핸들링
- 이미지 로드 실패 시 해당 패널을 REDO로 판정
- 2회 재생성 후에도 REDO인 패널은 경고와 함께 PASS 처리
```

6. 협업 - 팀 안에서의 위치 결정
   이 에이전트가 **누구와 어떤 순서로 연결되는지 명시한다.** 단, 단독으로 호출되는 서브에이전트라면 생략해도 된다.

```text
## 협업
- 상류: commit-message 스킬이 이 에이전트를 호출한다.
- 하류: commit-msg-reviewer가 이 에이전트의 draft를 읽는다.
- 재호출: reviewer 판정이 FIX/REDO일 때 스킬이 최대 2회까지 재호출한다.
```

7. 품질 자체 검증 - 제출 전 자기 점검
   출력을 반환하기 전에 **에이전트가 스스로 거쳐야 할 체크리스트**이다. 후속 리뷰어가 잡을 것을 에이전트가 먼저 잡으면 루프 횟수가 줄어든다.

좋은 예

```text
## 품질 자체 검증 (제출 전)
- [ ] 메타 데이터 주석 포함
- [ ] 분량 2,500 ~ 4,000 단어 범위
- [ ] Par별 포맷 필수 섹션 모두 포함
- [ ] 모든 수치, 인용에 출처 표기
- [ ] 용어 사전과 충돌 없음
- [ ] 코드 블록 컴파일/실행 가능 (의사코드면 명시)
- [ ] 크로스 레퍼런스가 실제 존재하는 장 가리킴
```

# 프론트매터 5개 필드

1. name, description - 언제 호출될지 결정

- name 은 파일명과 반드시 일치.
- descriptioin 은 오케스트레이터가 '이 에이전트를 언제 쓸지' 판단 하는 근거
  나쁜 예

```text
description: "세계관을 만드는 에이전트"
```

좋은 예

```text
description: "SF 소설의 세계관을 구축하는 전문가. 물리 법칙, 사회 구조, 기술 수준, 역사를 설계한다."
```

차이는 "무엇을 하는가"에 "구체적으로 무엇을 다루는가"를 더한 2축 구성에 있다. description 은 이름표가 아니라 호출 트리거이다.

2. model - 추론 깊이에 따른 결정
   model 필드는 비용, 모델 등급, 응답 속도를 한꺼번에 결정한다. 기본값은 inherit, 즉 부모 세션의 모델을 상속.
   결정 기준은 요구되는 추론 깊이. 쓰기 권한이 있든 없든 이 축과 무관.

3. tools - 부작용 범위에 따라 결정
   이 에이전트에게 허용할 도구 목록. 생략하면 부모 컨텍스트의 모든 도구가 상속. model 과 달리 이 축의 결정 기준은 **에이전트가 일으킬 수 있는 부작용의 범위**
   도구를 너무 많이 주면 역할과 무관한 도구 설명이 시스템 프롬프트에 들어가 토큰을 낭비하고, 에이전트가 본래 영역 밖으로 나갈 가능이 커진다.
   반대로 너무 적게 주면 작업이 조용히 실패한다.

예시

```text
---
name: security-analyst
description: "코드베이스의 보안 취약점을 식별한다.
              인증, 인가 문제, 주입 공격, 민감 데이터 노출 등을 탐지."
model: sonnet
tools: Read, Grep, Glob, Bash
---

# 보안 전문가

## 역할
코드를 읽고 분석하여 보안 취약점을 식별한다.
수정은 제안만 하며, 실제 코드 변경은 다른 에이전트가 수행한다.

## 작업 원칙
1. 읽기 전용으로 작동한다. (White, Edit 도구 사용 금지)
2. 취약점은 심각도(Critical/High/Medium/Low)로 분류한다
3. 각 취약점마다 위치, 설명, 권장 수정안을 제시한다.
4. CVE나 OWASP 기준을 참조한다.
```
